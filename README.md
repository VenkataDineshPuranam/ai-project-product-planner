# AI Project and Product Management Planner

Local-first, offline-capable planner combining Microsoft-Project-style
scheduling with AI product-management and AI/ML/LLM engineering lifecycle
tracking. See `docs/PRD.md` for the full product definition.

## Status

**Stage 9 complete: end-to-end production-readiness review.** See
`docs/PRODUCTION_READINESS_REPORT.md` for the full evidence-based
report. Summary: type checks, lint, all 176 unit/integration tests, a
new Playwright e2e smoke suite (3/3, against the real production
build), and a new automated accessibility scan (axe-core, zero
violations) all pass. A genuine 2 000-task performance bug was found
and fixed during this review (uncached `Intl.DateTimeFormat` +
day-by-day calendar iteration caused a 60+ second hang; replaced with
cached formatters and closed-form calendar arithmetic — now ~85–100 ms
for 500 tasks and ~207–340 ms for 2 000 tasks, both inside budget).

**Two real, named gaps remain** (not glossed over — see the report):
the rendered UI is not yet wired to IndexedDB persistence (the
persistence layer itself is fully tested, but editing a task in the
running app does not currently save anywhere), and grid/Gantt rendering
has no virtualization so its performance at 2 000 tasks in a real
browser is unmeasured.

**Stage 6 complete: resources, cost & AI FinOps.** Stages 1–5 are done.
This stage adds:

- `src/calculations/resources.ts` — `computeResourceHistogram` (per-resource,
  per-working-day sum of assignment units, calendar-aware) and
  `detectOverAllocations` (reuses the `OVER_ALLOCATION` warning type from
  the scheduling engine's error/warning vocabulary). Over-allocation is
  surfaced only — never auto-resolved by silently moving task dates, per
  `docs/PRD.md` §3/§19.
- `src/calculations/cost.ts` — `computeTaskCost`/`computeProjectCost`:
  resource cost from assignments × cost rate, plus fixed cost accrued per
  the task's `costAccrual` method (`start`/`end`/`prorated`); sums only
  leaf tasks to avoid double-counting summary rollups.
- `src/calculations/finops.ts` — `computeInferenceCost` (token volume ×
  per-million rate), `tokenBudgetAlert` (fires at/above a threshold ratio,
  not below), `costPerAcceptedOutcome` (returns `undefined`, never a
  fabricated 0 or Infinity, when there are no accepted outcomes), and
  `evaluateCostChange` — which directly encodes the FinOps rule from
  `docs/PRD.md` §12: a cost reduction only counts as `isGenuineImprovement`
  if quality did not also regress.

No new UI this stage either, consistent with the Stage 5 decision — these
are calculation/rule modules with tests; a resources/budgets panel is a
UI follow-up alongside the product/AI workspace UI from Stage 5.

### Known UI limitations (Stage 4, honestly documented)

- No DOM-node virtualization yet: the grid and Gantt render every visible
  row directly. This is fine for the current sample data but will need
  windowing before the 2 000-task / smooth-scroll performance budget
  (`docs/IMPLEMENTATION_PLAN.md`) can be verified — tracked for a later
  pass within Stage 4/9, not silently claimed as done.
- No drag-to-move, resize-to-change-duration, or drag-to-create-dependency
  interactions yet — selection, expand/collapse, and keyboard navigation
  are implemented; direct manipulation editing is a follow-up within this
  stage.
- Verified via component/integration tests (React Testing Library) and a
  manual dev-server smoke test (`curl` against the Vite dev server
  confirmed the page and module graph load without errors). This
  environment has no visual browser/screenshot tool, so the render was
  **not** visually inspected in an actual browser — noting that
  explicitly rather than claiming full manual verification.
- No Playwright e2e suite yet (`e2e/` is still empty) — planned for when
  drag/resize/print-view interactions exist to test end-to-end.

### Known scheduling-engine limitations (Stage 3, honestly documented)

- Free/total float and cross-day lag arithmetic use whole-minute rounding
  computed independently per quantity; this is accurate for real-world
  planning granularity (minutes) but is not exact to floating-point
  precision — acceptable for a project scheduler, called out here rather
  than left implicit.
- Resource calendars (as opposed to task/project calendars) are modeled
  in the domain but not yet factored into the CPM date computation itself
  — that lands with Stage 6 (resources & cost).
- Automatic resource leveling is out of scope entirely (by design, see
  `docs/PRD.md` §3).

## Getting started

```
npm install
npm run typecheck
npm run lint
npm test
```

There is no application UI yet (`npm run dev` shows a placeholder
screen) — the grid/Gantt UI is Stage 4. Playwright e2e tests (`e2e/`)
are not set up until there is a UI to test.

## Roadmap

See `docs/IMPLEMENTATION_PLAN.md` for the full 9-stage plan. Each stage
is a separate, reviewed increment — the project is deliberately not
built in a single pass.

## Excluded from v1

Real-time multi-user collaboration, cloud sync, native `.mpp`
import/export, enterprise SSO, external ticketing integrations, silent
automatic resource leveling, live model-provider billing ingestion,
production deployment actions, autonomous governance approvals. See
`docs/PRD.md` §3.

## No claim of Microsoft Project file compatibility

This application does not read or write `.mpp` files and makes no claim
of Microsoft Project compatibility beyond matching its scheduling
*semantics* (CPM, calendars, constraints, dependency types).
